# CA-15 Evidence Report

## Baseline

The CA-14 measurement harness (merged #419) fixed the timing/PID/exit-code
defects, and the owner review of #419 confirmed those closed — but
identified three remaining failure paths that could hang the harness
forever instead of failing within a bound:

1. `measure.ts` acquired a **fresh stdout reader per readiness-loop
   iteration**; a readiness line split across chunks would make the second
   `getReader()` throw a locked-stream TypeError (reproduced by the owner
   with standard Web Streams semantics).
2. The loop **parsed an origin without establishing that the complete
   readiness line had arrived** (pattern matched against a partial buffer).
3. **Deadlines were checked between awaits**: a silent child (blocking
   read), a hanging readiness response (fetch with no timeout), an unread
   body, and an unconditional `await proc.exited` on shutdown (child
   ignoring SIGTERM) could each stall the harness or its cleanup
   indefinitely.

The v2 measurement artifact from #419 is NOT invalidated by this repair;
its samples stand as recorded.

## Outcome

All three failure paths are now bounded, via a dedicated, directly tested
library:

- `readinessOrigin()` — exactly **one retained reader** for the whole
  wait, chunk-accumulated and split on newlines so only **complete lines**
  are matched; the timeout is a timer that **fires inside the await**
  (`Promise.race`), and the child is killed on the failure path.
- `waitForReady()` — readiness is a 200 with a **fully consumed body**;
  every attempt (fetch + consume) is individually raced against a firing
  timer, so a hanging response costs one attempt duration, never infinity.
- `stopServer()` — SIGTERM raced against `graceMs`, escalation to
  **SIGKILL** raced against `killTimeoutMs`; resolves with the real exit
  result in every case, safe on an already-exited child.
- `fetchOk()` / `fetchText()` — workload requests bounded across fetch
  AND body consumption; bare `AbortSignal` DOMExceptions are rethrown
  with request context.
- `measure.ts` rewired onto these primitives with unchanged measurement
  semantics (same phases, counts, settling, artifact identity); the
  report's harness string records the bounded failure paths; new
  artifacts are suffixed `-v3`.

## Acceptance mapping (owner review of #419 → evidence)

| Owner requirement | Evidence |
|---|---|
| "retain one reader, assemble a complete line" | `readinessOrigin` implementation; test "fragmented readiness output: one reader assembles the line; origin only from a COMPLETE line" (fixture splits the token mid-word across writes after an unterminated decoy line) |
| "enforce actual asynchronous deadlines" | `raceWithTimer` fires while blocked on read; tests assert elapsed ≥ ~deadline AND ≪ infinite for the silent child and the noisy-child cases |
| hanging readiness response cannot stall | test "hanging readiness response: bounded per attempt AND in total" (never-responding `Bun.serve` handler; ≥2 attempts observed, total bound held) |
| "bound shutdown with escalation if necessary" | test "ignored SIGTERM: stopServer escalates to SIGKILL within its bound" (escalated=true, elapsed < 3 s) and "graceful SIGTERM: the real exit code is retained without escalation" (exit 0, no escalation) |
| "Test fragmented readiness output, a silent child, a hanging readiness response, and ignored SIGTERM" | all four named scenarios have dedicated tests, plus: early-exit (fast EOF error), noisy non-matching output, already-exited no-op, non-2xx/stalled workload requests, losing-promise late rejection containment |

- The starter's caret dependency ranges keep floating between installs
  (no lockfile by design since setup refreshes the `file:` tarball);
  tests were made type-robust across that range rather than pinning —
  pinning policy is an owner decision (deferred).
- The fixtures' READY handshake exists because signalling a half-booted
  Bun child hits the default SIGTERM action (observed exit 143 in early
  test iterations); production measurement is unaffected since the real
  server signals readiness via its stdout line.
