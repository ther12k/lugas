# M6R8 — Complete Jsonify serialization model and enforce typed-response media-type ownership (#317)

## Baseline

- `main@16641d6` (post-M6R7 merge, PR #316; #314 closed; #315 M6R7-ATT open).
- Trigger: follow-up external review confirming M6R7 fixes 1, 2, 4 and flagging two remaining gaps. Every claim reproduced against the exact tree before registration (type probes for finding 1, a `createTestServer`/`createClient` runtime probe for finding 2).

## Findings verified against the exact tree (all confirmed)

1. **P2 — `Jsonify<T>` mis-modeled four stringify outcomes** (type-probed on `16641d6`):
   - `Jsonify<[() => void]>` → `[never]`; truth: `[null]` (array serialization substitutes `null` for elements that serialize to `undefined`, including function/symbol elements). Same for `[symbol]`.
   - `Jsonify<{ value: string | (() => void) }>` → `{ value: string }`; truth: the key can be absent when the function branch is taken, so the read type must carry `undefined`. Same for `string | symbol`, `number | (() => void)`, `X | undefined | (() => void)`.
   - `Jsonify<{ value: void }>` → `{ value: undefined }`; truth: `{}` (the key is always dropped — `void` was missing from the key filter union).
   - Nested `bigint` → `{ id: never }` is a defensible flag, but serialization throws `TypeError` before any wire representation exists; the doc wording over-claimed ("mirrors what reaches the wire").
2. **P2 (pre-existing, now load-bearing) — content-type overrides contradicted the typed client.** `json()` let caller headers win unconditionally while the client's `parseResponse()` decodes by the actual media type. Runtime-probed both directions: `json(200, { ok: true }, { "content-type": "text/plain" })` delivered the string `'{"ok":true}'` under an `{ ok: true }` brand; `text(200, '{"x":1}', { "content-type": "application/json" })` delivered the object `{x:1}` under a `string` brand.

## Outcome

Both findings fixed. Finding 1 is compile-time only; finding 2 is a new runtime rejection (fail-closed at response construction) with four new catalog diagnostics.

- **`Jsonify` completion** (`src/core/response.ts`):
  - `JsonifyElement<V>` now distributes over `V` and maps function/symbol/`undefined`/`void` members to `null` (array substitution), other members through `Jsonify` (`bigint` members stay `never` — see doc).
  - Object members whose declared type *may* serialize to `undefined` (`MayBeDropped<V>`: any union member extending `Function | symbol | undefined | void`) keep their key with `undefined` added to the read type; the key filter drops members that *always* do — now including `void`.
  - `Jsonify` doc comment rewritten: the `bigint` case is explicitly a throw-signal ("nothing reaches the wire from `json()` for such a body"), not a wire type.
- **Media-type ownership** (`src/core/response.ts`): each typed helper owns a compatible media type and rejects contradictory explicit overrides while constructing the response, via catalog-backed diagnostics (override detected through `new Headers(init?.headers)` so record/`Headers`/tuple forms and header-name casing normalize; media type compared lowercased with parameters stripped):
  - `json()` → `application/json` or `application/*+json` — `LUGAS_RESPONSE_001`
  - `text()` → `text/*` — `LUGAS_RESPONSE_002`
  - `problem()` → `application/problem+json` — `LUGAS_RESPONSE_003`
  - `empty()` → no body; any content-type override rejected — `LUGAS_RESPONSE_004`
  - Compatible overrides keep the documented precedence (caller wins), including the existing `json()` → `application/problem+json` precedence test (a `+json` subtype) and `text()` → `text/html`.
  - Runtime note: helpers execute inside handlers, so a rejection surfaces through the standard unexpected-error policy (redacted 500) — the same lifecycle as other handler-stage diagnostics.
- **Catalog** (`src/internal/diagnostics.ts`, `docs/diagnostics.md`): `RESPONSE` family added to `DiagnosticFamily`/`DiagnosticCode`; four catalog rows; diagnostics golden fixture regenerated via `bun run scripts/update-goldens.ts --apply` (+24 lines, additions only — the harness's mandated review-and-apply flow).

## Assumptions

- Type-level inference of runtime `Headers` values is deliberately not attempted (fragile, per the review); the boundary is enforced at construction instead.
- `application/problem+json` is accepted by `json()` (it is a `+json` subtype) — the existing precedence test depends on it and it is semantically JSON.
- A malformed override (`content-type: ;`) counts as present-and-incompatible and is rejected; parameters (`; charset=…`) do not affect compatibility.

## Security considerations

- The new runtime rejections are fail-closed at construction and carry only the normalized media type as scalar context (no payload/header data), consistent with the redaction conventions in the diagnostics registry.
- No decode path changed client-side; the mismatch class the rule removes could previously leak a JSON document as a string (or parse text as JSON) — both are now impossible through the typed helpers.

## Known limitations

- Raw `new Response(...)` handlers remain outside the brand/ownership system by design; the client widens them to `{ status: number; body: unknown }` (unchanged).
- `Jsonify` remains a model of own-enumerable data; prototype-getter-only classes are approximated by their declared property types (documented since M6R7).
- `problem()` bodies are still not `Jsonified` (deferred consistency follow-up, unchanged scope).
