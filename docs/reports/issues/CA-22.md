# CA-22 — Examples onboarding

Owner dispatch (2026-09-15): one bounded examples/onboarding PR using
existing Lugas APIs — make `examples/spa-starter` the canonical full-stack
onboarding example with one small feature documented end to end, add a
goal-based `examples/README.md` index, and add a raw-TS vs `lugas-dist`
compatibility walkthrough on the same unbundled entry. No framework
contract, export, release-gate, baseline, dist-tag, or publication change;
no frontend bridges; no new scaffold.

## Baseline

- `examples/spa-starter` demonstrated capabilities as islands (typed GET,
  validated mutation, cookie auth, multipart, SSE, SPA fallback) with a
  button-log UI: no list/empty/error UI states, no resource traced
  schema → service → AppContract → typed client → UI.
- `examples/README.md` was a flat concept table: no goal-based entry
  points, no prerequisites, no distribution-mode guidance, no
  published-vs-local labeling.
- The starter's `setup.ts` already stages the repo's dual-distribution
  package (dist built, `0.0.0-starter`), so `--conditions=lugas-dist` is
  exercisable against the installed candidate today.

## Outcome

1. **Tasks feature** — one resource traced end to end:
   - `server/tasks.ts` (NEW): `TaskCreateSchema` (Zod, shared by route
     validation and service input type) + an application-owned task
     service (in-memory store; documented as reset-on-restart, with
     `examples/drizzle` named as the database shape).
   - `server/app.ts`: four routes — `GET /api/tasks` (open; empty state),
     `POST /api/tasks` (validated; typed 422 with `issues[]`),
     `POST /api/tasks/:id/complete` and `DELETE /api/tasks/:id` (both
     behind the existing `requireSession` guard; typed 401/404 outcomes;
     declared `params` schema so `ctx.params.id` is validated and typed).
     No header slot declared: browsers carry the httpOnly cookie
     automatically (same-origin), matching the existing `/api/me` design.
   - `src/App.tsx`: `TasksPanel` renders loading / empty / error (+ retry)
     states, inline 422 `issues[]` under the form, and a 401 unauthorized
     state with a Sign-in action; stale 404s converge to server truth.
     The former demo buttons move under "More capabilities" as follow-on
     sections. Parameterized calls use the `:pattern` + `params` slot
     idiom (realworld precedent).
2. **Distribution-mode walkthrough** — `start:raw` / `start:dist` scripts
   on the same unbundled `server/main.ts`, and `scripts/verify-modes.ts`
   (NEW): proves the two invocations resolve different files of the same
   installed package (`src/index.ts` vs `dist/index.js`), that
   `FRAMEWORK_VERSION` is identical across package/src/dist, and that
   both modes return identical responses (status, content type, body)
   across the task routes, the 422/401 Problem Details, and the SPA
   shell. Compatibility check only — no timing or memory figures are
   measured or claimed. Production bundling is documented as a separate
   concern (build-time resolution). `verify:modes` is appended to the
   starter `verify` chain.
3. **Tests** — `tests/starter.test.ts` gains "tasks walkthrough" (empty
   state, 201, typed 422 with issues, 401 before login, 200/404/204 after
   login via raw fetch with explicit cookie — the existing `/api/me`
   precedent; the browser flow needs no header plumbing). All 11
   pre-existing starter tests and 11 harness tests unchanged and passing.
4. **Documentation** — `examples/spa-starter/README.md` rewritten as the
   guided tutorial (the five-layer chain, a route/outcome table, a
   user-action table, fail-then-pass script, follow-on sections,
   distribution modes with the no-benchmark framing, beta.5-npm caveat);
   `examples/README.md` gains the goal-based "Start here" table,
   prerequisites/expected results, locally-packed-candidate labeling, and
   the distribution-mode section (owner wording: raw default, optional
   pre-transpiled distribution, "not advertised as a faster
   request-processing mode").

## Security considerations

No new attack surface: routes are example-grade; the session guard, httpOnly
cookie, and secure headers are pre-existing. `verify-modes.ts` spawns local
processes on ephemeral ports with bounded deadlines and SIGTERM→SIGKILL
escalation (reused CA-15 primitives). No secrets, no tokens.

## Known limitations

- The task store resets on restart (documented in README and service
  header) — deliberate for an onboarding example.
- `verify:modes` parity covers representative routes, not every endpoint
  (sufficient for compatibility demonstration, which is its only claim).
- The `lugas-dist` walkthrough binds to the checkout's dual exports; the
  npm beta.5 caveat is documented rather than worked around.
