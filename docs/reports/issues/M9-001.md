# M9-001 — Drizzle ORM integration (`lugas/drizzle`)

Issue: [#357](https://github.com/ther12k/lugas/issues/357) · ADR: [ADR-0026](../../okf/decisions/0026-drizzle-integration.md) · Dispatch: [ODR-0010](../../owner-decisions/m9-001-dispatch.md)

Branch base: `c4ccff6` (merge of PR #358 — ADR-0026 + ODR-0010 on green main `bbf825e`, carrying the published beta.2 state).

## Baseline

`bun run verify` green on the base commit (typecheck, 784 tests, docs, diff). `lugas/drizzle` did not exist; the package export map was `{ ".", "./client", "./client/browser", "./testing" }`; the diagnostics catalog ended at `LUGAS_OPENAPI_001`/`002`. Applications could compose `service({ name, value: db })` directly, with no validation, no diagnostics, and no disposal wiring.

## Outcome

`lugas/drizzle` ships `drizzleService({ db, name, closeOnDispose? })`:

- Returns a `service()`-compatible descriptor (ADR-0020 machinery unchanged: init order, drain-ordered reverse disposal, deadline invariant). The service value is the application's Drizzle instance, reached by handlers through the typed `ctx.services.<name>` contract with the exact instance type preserved (compile-time pinned across two distinct Drizzle db type instantiations).
- Structural validation at declaration time: `select`/`insert`/`update`/`delete` must be functions, else `LUGAS_DRIZZLE_001`. There is no `instanceof`, no brand check, and **no drizzle-orm import anywhere in the package** — structural fakes are valid services.
- `closeOnDispose: true` wires dispose through the structural `$client.close()`; a non-closable (or absent) client fails closed at declaration with `LUGAS_DRIZZLE_002`. Default dispose is absent — application-owned shutdown.
- No implicit I/O: the adapter never sets `init`; no connection, query, ping, or migration runs at startup. No `migrate` export exists (pinned by test: the module surface is exactly `["drizzleService"]`).
- No transaction surface: nothing intercepts or wraps Drizzle transactions/savepoints.

## Assumptions

- The structural CRUD surface (`select`/`insert`/`update`/`delete` as functions) is present on every current Drizzle entry-point instance across drivers; `execute` deliberately excluded (absent on `bun-sqlite`, per probe).
- `closeOnDispose` covers only closable `$client`s; pools exposing `end()` compose `service()` directly (documented in `docs/drizzle.md` and the `LUGAS_DRIZZLE_002` hint).
- Disposal semantics tests use `lugasLifecycle.shutdown()` (graceful) because `createTestServer().stop()` force-closes, which by ADR-0020 never disposes.

## Security considerations

- The adapter adds no request-path code: services are values closed over by compiled handlers, and validation runs once at declaration. No new attack surface, no payload handling, no logging.
- `closeOnDispose` fail-closed behavior prevents a silent no-op dispose that could leak connections.
- No payload data ever enters diagnostics (codes carry `method`/`key` scalar context only).

## Known limitations / Not exercised

- PostgreSQL/MySQL integration lanes are not exercised (no server in CI); the adapter is driver-agnostic by construction and type-pinned on two Drizzle instantiations, but only Bun SQLite runs end-to-end. Recorded as deferred, not skipped.
- Structural validation proves intent, not a real Drizzle instance — the documented tradeoff of the no-import rule (ADR-0026 Consequences).
- Handlers reach the instance via `ctx.services.<name>`; there is no `ctx.db` guard alias (ADR-0026 Alternatives; revisit trigger recorded).
