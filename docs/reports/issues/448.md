## Outcome

1. **`tests/lifecycle/deployment-smoke.test.ts`** — real termination in an unprivileged container (`docker run --rm --user 1000:1000` with the repository mounted read-only, pinned `oven/bun:1.4.0-alpine`, `--network host` so the READY port is probed over a real socket). Three rows *(several claims in this list were corrected 2026-11-27 — see the erratum)*:
   - *Healthy drain*: READY → `/ready` 200 `{"status":"ready"}` and `/health` 200 `{"status":"ok"}` → **the client cancels its own stream** (that cancel is what runs `SSE-CLEANUP`) → `docker kill --signal=TERM` → wait for the fixture's `SIGTERM-HANDLED` marker → port stops accepting (probe fails to connect, not 5xx) → exit 0 within the bounded window → exactly one `DISPOSED`.
   - *Held stream at SIGTERM (observed fail-mode)*: stream left open → shutdown-time cleanup runs (`SSE-CLEANUP` after the marker), the open stream holds the shutdown until the 10s default budget expires, disposal is withheld, and the process still exits 0. Pinned as documentation of fail-mode, with a pointer to the lifecycle suite's disposal-withheld semantics; surfaced for owner review in this report (see Limitations).
   - *Failed startup*: init throws → `INIT-OK` then `ROLLBACK-DISPOSED` (one initialized service, so the container row proves rollback happened, not reverse order — order is pinned by the lifecycle suite's three-service fixture), never READY, non-zero exit, no lingering container.
   Skips cleanly when Docker is unusable or the image is absent (the hosted verify job executes the suite; its rows skip there for lack of the image — see the erratum for what that does and does not cover).
2. **`tests/lifecycle/deployment-failures.test.ts`** — in-process fail-modes, each pinned to probe-observed behavior (Bun 1.4.0/Linux): readiness answers 200 while ready and the port stops accepting once shutdown starts; SSE cleanup runs exactly once on server shutdown while disposal is withheld at budget expiry and the client's stream read terminates; on client disconnect the request **signal aborts** (observed via a listener) while an uncooperative handler — one that never reads the signal — runs to completion and its response is discarded (the README limitation, demonstrated rather than promised).
3. **`docs/production.md`** — new "Deployment runbook": the state table (starting/ready/draining/two stopped variants/failed-startup with probe and exit-code facts), the opt-in `shutdown.signals` requirement, the two easy-to-get-wrong facts (open SSE streams hold the shutdown — WebSockets do not, the framework closes them itself; disconnects abort the request signal but don't cancel uncooperative handler work), and an explicit app/framework/proxy responsibility split (TLS, the single shutdown budget, `/ready` as the traffic-shifting target, upload budgets, static-asset boundary). Synced to the site copy.

## Assumptions

- Docker with a loopback-host network is an acceptable "isolated deployment" for evidence purposes; the container is unprivileged (uid 1000), the repo mount is read-only, and the termination window is bounded with a SIGKILL watchdog.
- `oven/bun:1.4.0-alpine` is the deployment runtime; the suite pins it and skips when unavailable rather than silently passing.

## Known limitations / deferred work

- **Exit 0 with disposal withheld** (held stream at deadline) is now a pinned, documented deployment fact. Whether a withheld disposal *should* surface in the exit code is an owner question this evidence raises but does not decide — it is release-behavior design, out of the stabilization lane.
- The container smoke runs in the verify job but has never executed its rows there: the hosted runner has no Docker *image* — the suite loads, evaluates its Docker/image guard, and reports three visible skips. Every executed row to date ran on a local Docker host. Consequence: the three container scenarios (healthy drain, held-stream fail-mode, failed-startup rollback) have no continuous-integration coverage; they re-run only when a developer with the pinned image runs the suite. *(Corrected 2026-11-27: the original text said the suite was "not wired into any CI lane (no Docker on the hosted runners)" — the verify job does execute the suite; see the [erratum](#erratum-2026-11-27).)*

## Erratum (2026-11-27)

A post-merge review found one false statement, three claims the assertions did not support, and two test weaknesses; the Outcome and Acceptance text above is corrected in place, and the tests are fixed in this branch.

1. **The CI claim was wrong.** "Known limitations" originally said the container smoke was "not wired into any CI lane (no Docker on the hosted runners)". In fact the suite is wired into the verify job (the unfiltered `bun test` gate) and its guard evaluates there — the rows **skip** because the pinned `oven/bun:1.4.0-alpine` image is absent from the hosted runner, not because the suite is unwired. The substantive consequence is unchanged but now stated precisely: the three container rows have never executed on CI and have no continuous-integration execution; they run only on a local Docker host with the image present. If CI coverage of the container scenarios is wanted, that requires a runner with Docker plus the image (or a pull step) — an owner decision, recorded here rather than decided.
2. **`SSE-CLEANUP` was attributed to the wrong trigger in the healthy-drain row.** In that row the client cancels its own stream before the signal, and it is that cancel — not the SIGTERM drain — that runs the cleanup (`src/core/sse.ts` cancel path). The row's title and the report claimed shutdown-time cleanup. Corrected: the healthy row now documents the disconnect-path cleanup, and the held-stream row (which leaves the stream open through the signal) is the shutdown-time cleanup evidence. The drain probe also waits for a new `SIGTERM-HANDLED` marker the fixture prints from a listener registered *after* `app.serve()` — previously the probe could race the in-container handler before its synchronous `stop()`.
3. **"Reverse rollback, order pinned" overclaimed the failed-startup row.** The container fixture has exactly one initialized service, and the assertions are unordered `toContain` checks — the row proves rollback *happened*, not its order; reverse order is pinned by the lifecycle suite's three-service fixture. Reworded.
4. **"Every state transition asserted" overclaimed the container suite.** The starting state is never probed there (the fixture's init is near-instant); that behavior rests on `tests/production/production.test.ts`. The acceptance mapping now says which suite carries which state.
5. **The disconnect row could not fail.** The handler was a bare `Bun.sleep` + push, so "handler ran to completion" was guaranteed by language semantics regardless of any disconnect behavior. It now registers a listener on `ctx.request.signal`: the row asserts the signal aborts (the platform actually reporting the disconnect) *and* the uncooperative handler completes. The runbook bullet was likewise sharpened — Bun aborts the request signal on disconnect; handlers that never read it keep running.
6. **The watchdog and `finally` killed the `docker run` client, not the container** — a killed client leaves the `--network host` container running on the host loopback until cleanup. Overrun and failure paths now reap with `docker rm -f` (which stops the container), and every probe fetch carries an explicit timeout, so the "bounded termination window" in the header comment is now real rather than nominal.
7. **Minor**: `describe.skipIf` carries no skip-reason string (a Bun limitation of the guard form used); the skip is visible as a skip, not annotated. An unused `join` import was removed (typecheck passed anyway — `noUnusedLocals` is not enabled — so the gate could not catch it).
8. **Drain test oracle strengthened (LR2-05)**: The drain probe previously mapped any rejected fetch to `'not-accepting'`, so an accepted-but-hanging request falsely satisfied the drain check (demonstrated by `drain-oracle-negative-control.mjs`). Replaced with `probeDrainSocket` in `tests/lifecycle/deployment-failures.test.ts` and `deployment-smoke.test.ts` to actively require `'connection-refused'` (`ConnectionRefused` / `ECONNREFUSED` / `Unable to connect`), treating `'timeout'` or `'answered'` as failures. An in-process negative control confirms a hanging server yields `'timeout'` and fails the refusal expectation.
