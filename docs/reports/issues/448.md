**Not covered anywhere:** the drain state itself (what probes see between SIGTERM and exit), SSE under server shutdown, disconnect non-cancellation as a demonstrated fact, and any deployment-environment run (the subprocess SIGTERM child is still an in-process Bun child, not a container).

## Outcome

1. **`tests/lifecycle/deployment-smoke.test.ts`** — real termination in an unprivileged container (`docker run --rm --user 1000:1000` with the repository mounted read-only, pinned `oven/bun:1.4.0-alpine`, `--network host` so the READY port is probed over a real socket). Three rows:
   - *Healthy drain*: READY → `/ready` 200 `{"status":"ready"}` and `/health` 200 `{"status":"ok"}` → client closes its stream → `docker kill --signal=TERM` → port stops accepting (probe fails to connect, not 5xx) → exit 0 within the bounded window → `SSE-CLEANUP` + exactly one `DISPOSED`.
   - *Held stream at SIGTERM (observed fail-mode)*: stream left open → cleanup runs, but the open stream holds the drain until the 10s default deadline expires, disposal is withheld, and the process still exits 0. Pinned as documentation of fail-mode, with a pointer to the lifecycle suite's disposal-withheld semantics; surfaced for owner review in this report (see Limitations).
   - *Failed startup*: init throws → `INIT-OK` then `ROLLBACK-DISPOSED` (reverse rollback, order pinned), never READY, non-zero exit, no lingering container.
   Skips cleanly when Docker is unusable or the image is absent (CI lanes without Docker; the skip states the missing prerequisite).
2. **`tests/lifecycle/deployment-failures.test.ts`** — in-process fail-modes, each pinned to probe-observed behavior (Bun 1.4.0/Linux): readiness answers 200 while ready and the port stops accepting once shutdown starts; SSE cleanup runs exactly once on server shutdown while disposal is withheld at deadline expiry and the client's stream read terminates; a client that aborts mid-handler gets `AbortError` while the handler runs to completion (the README limitation, demonstrated rather than promised).
3. **`docs/production.md`** — new "Deployment runbook": the four-state table (starting/ready/draining/stopped with probe and exit-code facts), the two easy-to-get-wrong facts (open streams hold the drain; disconnects don't cancel work), and an explicit app/framework/proxy responsibility split (TLS, timeouts above the drain deadline, `/ready` as the traffic-shifting target, upload budgets, static-asset boundary). Synced to the site copy.

## Assumptions

- Docker with a loopback-host network is an acceptable "isolated deployment" for evidence purposes; the container is unprivileged (uid 1000), the repo mount is read-only, and the termination window is bounded with a SIGKILL watchdog.
- `oven/bun:1.4.0-alpine` is the deployment runtime; the suite pins it and skips when unavailable rather than silently passing.

## Known limitations / deferred work

- **Exit 0 with disposal withheld** (held stream at deadline) is now a pinned, documented deployment fact. Whether a withheld disposal *should* surface in the exit code is an owner question this evidence raises but does not decide — it is release-behavior design, out of the stabilization lane.
- The container smoke runs in the verify job but has never executed its rows there: the hosted runner has no Docker *image* — the suite loads, evaluates its Docker/image guard, and reports three visible skips. Every executed row to date ran on a local Docker host. Consequence: the three container scenarios (healthy drain, held-stream fail-mode, failed-startup rollback) have no continuous-integration coverage; they re-run only when a developer with the pinned image runs the suite. *(Corrected 2026-11-27: the original text said the suite was "not wired into any CI lane (no Docker on the hosted runners)" — the verify job does execute the suite; see the [erratum](#erratum-2026-11-27).)*
- Single-platform evidence: Linux x64, Bun 1.4.0, Docker 28. The compatibility matrix lanes remain the per-OS authority.
- Deployment-hardening items the issue mentioned that already exist elsewhere are linked from the runbook, not duplicated: upload budgets (`docs/body-limits.md`), static header boundary (`docs/spa.md`, corrected in the #449 erratum), redacted errors (error-policy suites).

## Erratum (2026-11-27)

A post-merge review found one false statement and two loose edges.

1. **The CI claim was wrong.** "Known limitations" originally said the container smoke was "not wired into any CI lane (no Docker on the hosted runners)". In fact the suite is wired into the verify job (the unfiltered `bun test` gate) and its guard evaluates there — the rows **skip** because the pinned `oven/bun:1.4.0-alpine` image is absent from the hosted runner, not because the suite is unwired. The substantive consequence is unchanged but now stated precisely: the three container rows have never executed on CI and have no continuous-integration execution; they run only on a local Docker host with the image present. If CI coverage of the container scenarios is wanted, that requires a runner with Docker plus the image (or a pull step) — an owner decision, recorded here rather than decided.
2. **Unused import**: `deployment-smoke.test.ts` imported `join` from `node:path` and never used it. Removed in this branch (typecheck passed anyway — `noUnusedLocals` is not enabled — so the gate could not catch it).
3. **The `dir.startsWith(ROOT)` assertion in the #447 consumer suite cannot fail as written**: the consumer directory is constructed under `mkdtemp(tmpdir())` before the assertion, so a hostile-future change that moved it under the repo would still be caught by the containment checks that follow, but the assertion itself is tautological today. Noted here rather than changed — it belongs to #447's owned files and a one-line edit inside an erratum for #448 would muddy ownership. Recorded for the next #447-adjacent dispatch.
