# M6R1-003 Evidence — Fix async pipeline completed-stage tracking and nullish output

## Baseline
- Base commit: `c777f34` (main, M6R1-005 merged)
- Issue: #258 (M6R1-003)
- Bun/TypeScript: 1.4.0 / 7.0.2, Linux x64

## Outcome

Completed. `executeAsyncPipeline()` in `src/internal/compile-pipeline.ts` now
uses `key in partialContext` to determine whether the synchronous caller already
completed a stage, rather than a fresh empty `Set<string>`. The nullish
coalescing `partialContext.params ?? rawParams` is replaced with an explicit
presence check, so a validator whose legitimate output is `undefined` or `null`
is preserved rather than silently replaced with unvalidated raw params.

## Root causes fixed

**Defect 1 — double invocation**: `executeAsyncPipeline` created
`const completed = new Set<string>()` on every call. Stages already resolved
by the sync caller were never added, so `!completed.has('headers')` was always
`true`, re-running the schema a second time for the same request.

**Defect 2 — nullish coalescing on stage output**: `partialContext.params ?? rawParams`
treated `null`/`undefined` transformed values as "not set", falling back to raw
URL params. `key in partialContext` correctly distinguishes "stage already ran
and produced nullish output" from "stage not yet run".

## Security considerations
Correct completed-stage tracking prevents a validator from being called twice
for one request, which matters for validators with side-effects (e.g. rate-limit
increment). Nullish-output preservation ensures the handler always receives the
schema-transformed value, not raw user input.

## Known limitations / deferred
The body-schema path (`bodySchema !== undefined`) is a separate `async` closure
that does not go through `executeAsyncPipeline`; it was already correct (no
partial context handoff needed). This fix targets only the sync-then-async
escalation path.
