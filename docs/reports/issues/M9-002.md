## Outcome

Two additive root exports implement the ADR-0027 contract in one pure module (`src/core/cookies.ts`, no pipeline, no config):

- **`parseCookies(request)`** — RFC 6265 §5.4 parsing of the `Cookie` header into `Record<string, string>`. Lenient by design: malformed pairs skipped (never thrown), duplicates last-wins, `$`-prefixed reserved segments skipped, no header → `{}`, quotes preserved. Interpretation (percent-decoding, JSON) stays application-owned.
- **`cookie(name, value, attrs?)`** — strict `Set-Cookie` serialization with typed attributes (`httpOnly`, `secure`, `sameSite`, `path`, `domain`, `maxAge`, `expires`, `partitioned`). Fails closed at call time: invalid name/value tokens → `LUGAS_COOKIE_001`; invalid attributes or combinations (`SameSite=None` without `Secure`, empty path/domain, non-integer/non-finite maxAge, invalid expires, non-object attrs) → `LUGAS_COOKIE_002`. Grammar enforced by RFC 6265 §4.1.1 token/cookie-value regexes (6265bis control exclusions included). Composes with `json`/`text`/`problem` through `init.headers` as `[name, value][]`, preserving multiple `Set-Cookie` headers per response.
- **No auth product:** no signing, store, CSRF, or identity (ODR-0010 standing non-goals). The Better Auth interop ships as the documented guard recipe in `docs/cookies.md`.
- **Diagnostics:** `LUGAS_COOKIE_001`/`LUGAS_COOKIE_002` in the union + catalog; goldens regenerated (catalog only; no hint-bearing codes changed).

## Assumptions

- `parseCookies` returns raw parsed values (quotes preserved) — documented in `docs/cookies.md`; decoding is deliberately application-owned.
- Serialization attribute order is canonical (Max-Age, Expires, Domain, Path, Secure, HttpOnly, SameSite, Partitioned) — order is not semantically meaningful to RFC 6265 consumers but is deterministic for tests.
- `expires` accepts only a valid `Date` (no number/string coercion) — `maxAge` is the documented preference.
- The Better Auth recipe in `docs/cookies.md` is documentation, not a dependency; no auth library is imported anywhere.

## Security considerations

- Read path is hostile-input-safe: no throw, no allocation beyond the map, no header value reflected into diagnostics (context carries only truncated names).
- Write path fail-closed prevents malformed headers and the silently-rejected `SameSite=None`-without-`Secure` combination from reaching browsers.
- No payload/cookie data enters diagnostics (scalar name context only, truncated to 64 chars), matching the redaction convention.
- `parseCookies` does not decode — no decode-bomb (percent-decoding is application-owned by design).

## Known limitations / Not exercised

- `Set-Cookie` on `redirect()` uses the same `init.headers` composition and was not separately asserted (redirect owns no body/media-type conflict with cookie headers).
- Cookie prefixes (`__Secure-`, `__Host-`) are not specially validated — they pass the token grammar; enforcement guidance belongs in application review (noted in docs).
- `partitioned` is serialized without checking `secure` (the CHIPS spec couples them); browsers ignore `Partitioned` without `Secure` — acceptable as attributes are caller-owned, but worth a future tightening decision.
