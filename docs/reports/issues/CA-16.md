# CA-16 Evidence Report

## Baseline

- Base commit: `3a5bdef` (Merge pull request #421)
- Branch: `agent/CA-16-test-and-evidence-strengthen` / Worktree: `.worktrees/CA-16-followup`
- Bun version: 1.4.0 (x64 Linux)

Profiling of `src/internal/prepared-app.ts` identified two efficiency opportunities in request and initialization paths:
1. **Traffic gate continuation on every request**:
   ```ts
   // Previously in gateHandler:
   return Promise.resolve(trafficGate.gate).then(
     () => handler(request),
     () => problem(503, ...),
   );
   ```
   Even after service initialization settled (`trafficGate.settled === true`), every incoming request was wrapped with a `Promise.resolve().then(...)` microtask continuation, adding unnecessary microtask queue scheduling on synchronous route returns.
2. **Unconditional WebSocket hub construction**:
   `createWebSocketHub()` (allocating a Map, a Set, and closures) was executed during `prepareApp()` even when zero WebSocket routes were declared in the application.

## Outcome

1. **Lifecycle gate fast path**:
   `gateHandler` now checks `if (trafficGate.settled) return handler(request)`. When initialization is complete, handlers are invoked directly without scheduling a microtask continuation.
   - When initialization is pending (`settled === false`), requests continue to wait on `trafficGate.gate`.
   - When initialization fails (`settled === false`), requests take the rejection continuation and receive a redacted 503 problem.
   - When an application defines zero lifecycle services (`lifecycleServices.length === 0`), `trafficGate.settled` is immediately `true` upon `app.serve()`.
2. **Conditional WebSocket hub**:
   `createWebSocketHub()` is now constructed lazily only when the first WebSocket route descriptor is encountered during preparation. When no WebSocket routes exist, `prepared.websocketHub` remains `null`, avoiding the allocation while preserving the `PreparedApp` contract.

### 3. Paired Steady-State HTTP Measurements (Reproducibility Record)

- **Methodology & Rig**:
  - Pinned runtime: Bun 1.4.0 (x64 Linux).
  - CPU Counter: `/proc/<pid>/stat` fields 14 (`utime`) and 15 (`stime`) divided by `CLK_TCK` (100 Hz).
  - Concurrency: 8 parallel workers, full HTTP response body consumption (`res.arrayBuffer()`).
  - Warmup: 500 requests before each measured round.
  - Execution order: Interleaved round-robin (`continuation` R1 → `fast-path` R1 → `continuation` R2 → ...), 500 ms pause between runs.
  - Machine load during run: `/proc/loadavg` recorded per round.

## Security considerations

- Initialization failure continues to redact all internal error details behind the standard RFC 9457 Problem Details 503 response.
- `withErrorPolicy` continues to wrap the pipeline inside the traffic gate, ensuring unhandled exceptions in handlers or guards never escape to Bun's development error page.

## Known limitations

- The fast path benefits synchronous route returns after initialization has settled. Asynchronous handlers still return Promises which naturally queue on the microtask loop.
- The 1.4% median CPU reduction reflects the small per-call cost of microtask continuation allocation; the primary latency benefit is in reducing p99 tail queuing.
