## Outcome

Completed. Different methods on one path merge into one frozen method map across owners, order-independently; identical-method duplicates and any-method-vs-method overlaps fail closed with stable diagnostics.

## Assumptions

Recorded before coding:

1. **Composition stays the ownership referee.** `compose()` continues to reject exact `(method, path)` re-declarations across owners (`LUGAS_ROUTES_001`, unchanged). The merge work happens in `prepareApp()` over the declarations that survived composition.
2. **Different methods on one path merge** into a single frozen method map per path — across root/module/module boundaries, in any declaration order. Result is order-independent; swapping module order cannot change the served surface. This closes review finding P0-1 (last-module-wins whole-path overwrite in assembly).
3. **Wildcard/any-method vs explicit-method overlap fails closed.** Pinned Bun oracle fact: `Bun.serve({ routes })` holds exactly one value per path string; when both an any-method value and a method-map target the same path, raw Bun resolves by insertion order — precisely the silent order-dependence Lugas forbids. Decision: such overlap throws `LUGAS_ROUTES_001` at `defineApp()` with a precise message naming both owners and the path. Codes stay frozen; message wording documents the conflict class. Users express combined surfaces by declaring all methods explicitly in one method map.
4. **Any-method sources** (all produce `"*"` claims in composition): bare `route()` descriptors, plain functions, native `Response`/`BunFile`, `{ dir }`. Two any-method declarations for one path remain impossible past composition (already fatal there); a defensive second-check in assembly throws rather than silently overwriting.
5. **Manifest untouched** (owned by M4R1-008). For merged paths the existing manifest already records one record per method — now truthful against the merged runtime map. Overlap-conflicting configurations never reach a manifest because `defineApp()` throws before one is exposed.
6. **No public API change.** `defineApp/defineModule/route/guard` signatures untouched; behavior-only correction inside kernel-composition owned files.
7. **Diagnostics**: exact-duplicate message/wording unchanged; overlap uses `LUGAS_ROUTES_001` with context `{ method: "*", path }` so machine consumers see one stable conflict family. Catalog `meaning` row for `LUGAS_ROUTES_001` broadened slightly in docs wording only ("duplicate/conflicting route ownership").

### Implementation notes

- `prepareApp()` now groups declarations by path (root first, then modules in order), tracks per-method ownership, and validates before compiling:
  - two any-method claims on one path -> `LUGAS_ROUTES_001` (defensive; composition normally pre-empts);
  - any-method claim + any explicit method claim -> `LUGAS_ROUTES_001` naming the any-owner and the first method owner (pinned-oracle enforcement — raw Bun would resolve by insertion order);
  - exact-method duplicate reaching assembly -> `LUGAS_ROUTES_001` (defensive second layer under compose()).
- Merged maps are frozen; compilation and error-policy wrapping unchanged per method value.

## Type/runtime/bundle impact

- Runtime behavior correction only; no type or public API changes. Configurations that previously silently lost methods now either serve them (different-method merge) or fail fast at defineApp() (overlap).

## Security considerations

- Closes silent route-loss: previously a later module could shadow earlier methods at runtime while composition/manifest claimed availability — a route-surface integrity issue. Fail-closed overlap diagnostics prevent accidental exposure surprises.

## Known limitations

- Combining an any-method value with named methods on one path is rejected rather than merged; users express such surfaces by declaring all methods explicitly. Documented in assumptions (#3).
- Manifest still derives from composition (M4R1-008 owns regeneration from the prepared graph).
