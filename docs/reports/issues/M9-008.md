## Outcome

One new module (`src/core/rate-limit.ts`) exporting three runtime values and five types:

- **`rateLimit(config)`** — guard factory composed through the ordinary guard pipeline (`before: [rateLimit({...})]`). Config: `limit`/`windowMs` (positive integers), `store` (application-owned `RateLimitStore`), optional `key` (`(ctx) => string`), `keyPrefix` (namespacing string), `message` (429 body override). Unknown keys fail closed like every other factory.
- **Fixed-window semantics:** first hit in a fresh window returns `count: 1` from the store; `count <= limit` passes with `{ rateLimit: { limit, remaining, resetAt } }` enrichment (standard guard enrichment — typed into handler context, verified compile-time and at runtime through a real server); `count > limit` short-circuits `429` with `Retry-After` (integer seconds from the store's `resetAt`, min 0), `RateLimit-Limit`, `RateLimit-Remaining: 0`, `RateLimit-Reset` (delta seconds matching `Retry-After`), and an RFC 9457 Problem Details body (`type: https://lugasjs.dev/problems/rate-limited`) unless `message` overrides it (`text/plain`; the retry headers survive the override — verified).
- **Store contract (structural, no import):** `get(key) => Promise<Snapshot|undefined>` and `increment(key, windowMs) => Promise<Snapshot>`; `resetAt` is epoch milliseconds and expiry is entirely store-owned. Proven structurally: a hand-rolled fake store with an injectable clock drives the whole suite — window expiry admits again with **no real sleeping** (fake clock rolls past `resetAt`; the guard never touches timers for admission).
- **Keying:** default is the whole-request bucket (Lugas guards see only the `Request`; no `X-Forwarded-For` trust is invented). Custom `key` verified with per-API-key buckets (two keys stay independent); `keyPrefix` verified isolating two apps sharing one store.
- **Ordering is scoping:** `rateLimit` declared after an authenticate-style guard counts only authenticated hits (failed auth short-circuits before counting — verified); declared before, all traffic counts.
- **`createMemoryRateLimitStore()`** — reference store for tests/examples: non-durable, single-process, unbounded, documented as not-the-product.
- **Diagnostics:** `LUGAS_RATE_LIMIT_001` on every invalid shape (non-integer/non-positive `limit`/`windowMs`, non-object store, store missing `get`/`increment`, non-function `key`, non-string `keyPrefix`/`message`, unknown keys, non-object config) — union + catalog; goldens regenerated (+1 row, reason recorded here).
- **Typing:** the descriptor is `GuardDescriptor<TServices, Promise<{ rateLimit: RateLimitInfo } | Response>>`; the async result distributes correctly through `GuardContribution` (`Exclude<Awaited<Result>, Response>`) — `ctx.rateLimit` is `{ limit; remaining; resetAt }` (all readonly numbers) in handlers and later guards, and composes with an earlier auth guard's enrichment without collapsing to `never` (compile-time tests `_t1`–`_t4`).

## Assumptions

- `RateLimit-Reset` is emitted as delta-seconds (matching `Retry-After`); the IETF draft permits delta or epoch — documented in `docs/rate-limit.md`.
- `resetAt` is epoch milliseconds by contract; `Retry-After` math therefore uses real time. The fake-clock store sets small non-epoch values, so its 429s legitimately report `Retry-After: 0` — the expiry test asserts admission, not header math; the epoch-contract test uses the real memory store (`retry-after: 60` exact).
- Fixed-window burst (2× across a boundary) is accepted semantics, documented under "Fixed windows" — sliding windows/token buckets are an explicit future ADR, not interface drift.
- Two `rateLimit()` guards on one route collide on the `rateLimit` enrichment key and fail closed via `LUGAS_GUARD_007` — intended, documented.
- The memory store is intentionally unbounded (reference material, not production); the docs say so twice.

## Security considerations

- No key derivation from spoofable headers by default; the docs make per-client keying an explicit application decision (including a trusted-header recipe).
- The 429 body never echoes the bucket key or store internals.
- Rate limiting is defense-in-depth, not a security boundary; the docs position it as such.
- No new inputs are parsed; the guard trusts only the application-supplied store.

## Known limitations

- Fixed-window semantics only; boundary burst documented (deliberate minimalism per ADR-0034).
- Single `rateLimit` guard per route (enrichment-key collision fails closed rather than nesting).
- The default whole-request key is a global bucket when no `key` is supplied — documented, fail-closed, but applications behind proxies must supply `key`.
