## Outcome

Completed. Required structured input is now a compile error when omitted; explicit `body: null` transmits JSON null; HEAD responses never raise decode errors.

## Assumptions

1. **Conditional tuple signature.** `ClientMethod` becomes a rest-tuple signature: the whole input argument is required exactly when the route requires any of params/query/headers/body; otherwise it stays optional. Per-slot requiredness inside the object is unchanged (existing `MethodCallInput` composition).
2. **Requiredness derivation** reuses existing slot primitives so there is one source of truth:
   - params required ⇔ `keyof PathParams<P>` is not `never`;
   - query/headers/body required ⇔ their `Method*Input` slot is not `{ readonly x?: undefined }`.
3. **Body presence vs value (intentional contract correction).** Old documented behavior — "`null` means no body" — is corrected to: omitted key or `undefined` → no request body; explicit `null` → literal JSON `null` with JSON content-type semantics. The merged test asserting the old contract (`tests/unit/client-request.test.ts` "absent or null bodies send nothing synthetic") is updated to the corrected contract; this is an owned behavioral correction demanded by the issue's acceptance probe (`body: null` transmits JSON null), not a weakened assertion.
4. **HEAD/bodiless decode safety is runtime-truth based**: `readBody()` treats `response.body === null` as bodiless regardless of content-type. This covers HEAD responses (fetch yields null bodies) without threading method through signatures, and also covers any genuinely empty body generally.
5. **Negative type tests** live in `tests/types/client-required-input.test-d.ts` using `@ts-expect-error` on calls that omit required input objects, against a real `AppContract` fixture.
6. **Escape hatch untouched**: `client.request(method, path)` keeps its raw shape (no input object exists there by design).
7. **No Proxy / no runtime contract representation** — all new logic stays compile-time except the two runtime fixes above.

### Amendment (recorded after first implementation pass)

- Bun 1.4 fetch may expose a non-null empty body stream for HEAD responses, so a pure `response.body === null` check is insufficient on the pinned platform. Fix threads `options.method` into `parseResponse()` explicitly; the `body === null` check remains as an additional truthful guard.

## Type/runtime/bundle impact

- Types: `ClientMethod` signature change is the intended public-surface correction (required-input enforcement). New exported helper type `RequiresInput`. No new runtime exports.
- Runtime: `parseResponse` gains optional second parameter (backwards compatible); `buildRequestInit` null-body behavior corrected per issue.
- Bundle: negligible (+~40 lines).

## Security considerations

- Header diagnostics unchanged (values never serialized into errors).
- Null-body transmission follows caller intent exactly; no silent dropping that could mask schema mismatches.

## Known limitations

- Escape hatch `client.request(method, path)` remains untyped by design (no input object exists there).
- Literal objects cannot express "Response-like" rejection at the type level; runtime enrichment rules are owned by the pipeline (#197).
