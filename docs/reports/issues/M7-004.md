## Outcome

Services can declare async `init`/`dispose`; shutdown follows the accepted fixed order with three distinct outcomes and the ADR-0020 invariant.

**Public surface (small, explicit, object-based):**

- `service({ name, value, init?, dispose? })` — decorates one `defineApp({ services })` entry. Typed as `T` so handler context typing is unchanged; runtime value is a frozen brand-checked descriptor. Invalid descriptors throw `LUGAS_LIFECYCLE_001` (new catalog entry + goldens).
- `app.serve()` returns the Bun server augmented with a non-enumerable `lugasLifecycle` handle: `ready` (init completion; rejects after startup failure), idempotent `shutdown()` (resolves the SAME `ShutdownOutcome` object to every caller), `track(task)` (registers application work the drain waits for), and `ShutdownOutcome { connectionsClosed, trackedWorkCompleted, disposalCompleted, cooperated, deadlineExpired, disposalFailures }`.
- `serve({ shutdown: { drainDeadlineMs?, signals? } })` — drain deadline (default 10s, poll 15ms) and opt-in SIGINT/SIGTERM handling through the identical shutdown path.

**Serving-signature decision (ODR-0005 §2):** ODR-0005 permitted an async `serve()`. Implementation chose the non-breaking alternative: `serve()` stays synchronous and Lugas handlers are **gated** on the init promise (a per-app `trafficGate` captured at compile time, awaited by every compiled handler before execution). Observed behavior matches the ADR contract — no handler runs before services are ready — while ~50 existing `serve()` call sites (tests, examples, README drift-guarded fixtures, ColorJoy) remain untouched. Deviation from the ADR's literal "before the server accepts traffic": connections may be accepted during initialization, but held; documented in `docs/api-reference.md`. Startup failure: reverse-order rollback disposal, `ready` rejects with the original error, held requests receive a redacted `503` problem.

**Ordering implemented exactly as accepted:**

1. Stop accepting (`server.stop()`) — connections closed.
2. Drain: poll `pendingRequests === 0` AND tracked tasks settled, until the deadline. Shutdown awaits `ready` first, so disposal never races initialization.
3a. Drained in time: reverse-order disposal; every disposal failure is collected into `disposalFailures`; all outcomes `true`/`cooperated: true`.
3b. Deadline expired: `server.stop(true)` force-closes connections; outcome `trackedWorkCompleted: false`, `disposalCompleted: false`, `cooperated: false`, `deadlineExpired: true`; **services are deliberately not disposed** — continuing work observes an intact resource (invariant), and disposal is left to the application/supervisor boundary. No implicit process exit.

**Live-reference regression caught and fixed:** the first draft copied plain service values into a handler view, breaking the M4R1-001 live-reference test (mutations of the user's services object were invisible). Final design prototype-chains the view to the user's services object (live lookups preserved) and shadows only `service()` descriptor keys with fill-on-init slots, so raw descriptors are never exposed.

## Security considerations

- Startup-failure and 503 responses are redacted problem documents; the original init error is never reflected to clients (only to stderr with the `[lugas]` prefix and to the `ready` rejection for application handling).
- Signal handlers exist only under explicit `signals: true`, are removed at shutdown, and never call `process.exit`.

## Known limitations / Not exercised

- Native route values (plain functions, `Response`, `Bun.file`, `{ dir }`) and asset routes bypass the pipeline and are therefore not lifecycle-gated — documented, consistent with their existing bypass semantics.
- Drain uses 15ms polling rather than a completion callback (Bun exposes no request-completion hook); deadline accuracy is bounded by the poll interval.
- macOS/Windows were not exercised in this session; the lifecycle layer is platform-neutral (no OS-specific APIs beyond opt-in signals).
