# M6R9 — Strong typed-wire contract: non-finite numbers, toJSON-drop propagation, optional presence (#319)

## Baseline

- `main@15ae206` (post-M6R8 merge, PR #318; #317 closed; #315 M6R7-ATT open, re-anchored per wave).
- Trigger: follow-up review confirming M6R8's acceptance and identifying the remaining distance between `Jsonify`'s "compile-time mirror" wording and three concrete serialization classes, plus one root-body hole. The review offered a bounded-beta (wording-only) or a strong end-to-end contract; per its recommendation this wave implements the **strong contract** before the #315 quiet-host attestation is spent.
- All findings reproduced against the exact tree before implementation (type probe + `JSON.stringify` runtime probe: `{"value":null}` for NaN/Infinity, `{}` for the toJSON-dropped member, `[null]` for the toJSON-dropped element, `JSON.stringify(undefined)` → `undefined`).

## Findings and outcomes

1. **Non-finite numbers** — general `number` widens to `number \| null` (`JsonifyNumber<N> = number extends N ? N \| null : N`); finite numeric literals (`42`, `1.5`) stay exact. `json(200, { n: NaN })` now brands `n: number | null`, so `result.data.n.toFixed(2)` is a compile error instead of a runtime crash.
2. **`toJSON`-drop propagation** — members whose serialization ends in `undefined` (via any `toJSON` chain) are classified as dropped; in objects they are removed when always-dropped and become optional when possibly-dropped; in array elements they substitute as `null`.
3. **Optional presence** — possibly-dropped members become true optional properties (`{ value: string | (() => void) }` → `{ value?: string }`), not required keys padded with `undefined`; always-dropped members are removed entirely (M6R8 behavior preserved); never-dropped members stay required.
4. **Root no-JSON-text bodies** — `json()` now serializes first and throws `LUGAS_RESPONSE_005` when `JSON.stringify(body) === undefined` (root `undefined`, functions, symbols, or objects whose `toJSON` yields `undefined`), instead of constructing a null body with a JSON content type that the client would fail to decode. Root `null` stays valid. Root `bigint` keeps its natural native throw (documented throw-signal).
5. **Bookkeeping correction (accepted)** — the M6R8 close-out reported "8/8 CI checks green"; the PR exposes **7** named checks (6 compatibility cells + verify). The merge was verified green; the count was misreported. This report supersedes that number.

## Implementation notes

- **Drop analysis piggybacks on `Jsonify` itself** (`MemberDrops<V> = [Jsonify<V>] extends [never]`, with `[V] extends [bigint]` excluded as the throw case) instead of a separate recursion. Reason: the first implementation used a recursive conditional (`DropsToUndefinedSingle` through `toJSON` chains) evaluated inside mapped-type `as` clauses and then inside `{…}[keyof T]` keyset computation; under `tsc 7.0.2` both deferred evaluations misfired for single non-union members requiring recursion (standalone concrete evaluation returned `true`, in-keyset evaluation lost the key entirely — probed). Reading the decision off a pre-evaluated flag object (`DropFlags<T> = { [K in keyof T]: MemberDrops<T[K]> }`) evaluates correctly per key.
- **Object position** = `Simplify<{ [K in RequiredKeys<T>]: Jsonify<T[K]> } & { [K in OptionalKeys<T>]?: Jsonify<T[K]> }>`: required (never drops) / optional (may drop) / removed (always drops). The two branches flatten so the brand stays identity-comparable with plain object literals (`Equal`-based assertions would otherwise see `{ ok: boolean } & {}`).
- **Non-homomorphic mapping trade-off**: `readonly` modifiers on body types are not carried into the brand (wire payloads are freshly decoded values); documented in the `JsonifyObject` comment.
- **`any`-valued members stay required with value `any`**: tsgo resolves the tuple-wrapped checks to `false` for `any`, and `any` already reads as `undefined`-tolerant; locked by `_t17`.
- Diagnostics: `LUGAS_RESPONSE_005` added to the union, family catalog, `docs/diagnostics.md`, and the regenerated golden fixture.

## Assumptions

- The strong contract is the right pre-beta boundary (reviewer-recommended): the typed client is a headline feature and non-finite→null is a normal JavaScript case.
- `readonly` loss in the brand is acceptable: bodies are caller-side in-memory values; the brand describes the freshly decoded client value.
- Root-body rejection (005) is consistent with the M6R8 media-type ownership philosophy: `json()` owns bodies that produce JSON text.

## Security considerations

- `LUGAS_RESPONSE_005` carries no context (nothing observable about the body); the body never reaches the wire. No redaction surface changed.

## Known limitations

- `bigint` bodies throw natively (`TypeError` from `JSON.stringify`) before `json()` can produce a response; typed `never` as a throw-signal — deliberate, documented.
- `readonly` modifiers on body types do not survive into the brand (documented above).
- `any`-valued members remain required with value `any` (tsgo resolves the drop checks to `false` for `any`); `any` reads are already `undefined`-tolerant.
- `Jsonify` models own-enumerable data; prototype-getter-only classes approximate via declared property types (documented since M6R7).
